## Хэсэг A: Category-Partition гараар (Шилжүүлгийн функц)

### A1. Сонголт ба төлөөлөх утгууд
Шилжүүлгийн API (`POST /transfer`) оролтуудын сонголтууд:

| Параметр | Сонголтууд (Categories) | Төлөөлөх утгууд (Representative Values) |
| :--- | :--- | :--- |
| **from** (Шилжүүлэгч данс) | Valid, Frozen, Missing | `acc_101` (идэвхтэй), `acc_frozen` (царцаасан), `""` (байхгүй) |
| **to** (Хүлээн авагч данс) | Valid, Missing, SameAsFrom | `acc_102` (өөр данс), `""` (байхгүй), `acc_101` (from-той ижил) |
| **amount** (Мөнгөн дүн) | Normal, Zero, Negative, OverBalance, OverLimit | `500.0` (хэвийн), `0` (тэг), `-100.0` (сөрөг), `50000.0` (үлдэгдлээс их), `20000.0` (лимитээс их) |
| **currency** (Валют) | Same, Different | `"MNT"` (адил), `"USD"` (өөр — ханшийн хөрвүүлэлт шаардах) |

### A2. Хязгаарлалтууд ба Тооцоолол (N → M)
* **Тэмдэглэгээний үндэслэл:**
  * `[ERROR]`: Утга буруу эсвэл дүрэм зөрчсөн үед шууд алдаа буцаана.
  * `[SINGLE]`: Тухайн категорийн зөвхөн нэг төлөөлөгчийг тестлэхэд хангалттай.
  * `[IF/property]`: Оролт байхгүй (`Missing`) үед Amount зэрэг бусад параметрийн шалгалтыг алгасах нөхцөл.
* **Комбинацийн тооцоо ("N → M"):**
  * Бүрэн олонлогийн нийт боломжит комбинаци: $3 \times 3 \times 5 \times 2 = 90$ (`N = 90`).
  * Хязгаарлалт болон [SINGLE] дүрэм хэрэглэсний дараах бодит тест кейсийн тоо: `M = 14`.

## Хэсэг B: PICT — Pairwise covering array

### B1. Мөрийн тооны харьцуулалт ба Greedy алгоритмын тайлбар
* PICT нь хамгийн цөөн тест кейс олохын тулд **Greedy (шунахай)** алгоритм ашигладаг бөгөөд хосуудыг аль болох хурдан хамруулахын тулд хамгийн цөөн комбинацийг **заавал** олдоггүй. Тиймээс гар аргаар хүний оновчтой олсон цөөн мөрөөс зарим үед PICT бага зэрэг илүү мөр үүсгэдэг.

| Загвар (Model) | Хосолтын түвшин | Мөрийн тоо (Headers оролгүй) | Тайлбар |
| :--- | :---: | :---: | :--- |
| **browser.model** | 2-way | **10** | `results/browser-2way.txt` |
| **browser.model** | 3-way | **20** | `results/browser-3way.txt` |
| **transfer-nc.model** | 2-way | **13** | `results/transfer-nc.txt` (Хязгаарлалтгүй) |
| **transfer.model** | 2-way | **13** | `results/transfer.txt` (Хязгаарлалттай) |
| **transfer-neg.model** | 2-way | **16** | `results/transfer-neg.txt` (`~` сөрөг утгатай) |

### B2. Бодит тест кейсүүд
| № | Тест кейсийн төрөл | Setup (Бэлтгэл орчин) | Input Body (Оролт) | Oracle (Хүлээгдэх үр дүн) |
|:---|:---|:---|:---|:---|
| **1** | Happy Path | `acc_101` (Үлдэгдэл: 10,000 MNT), `acc_102` (Идэвхтэй) | `{"from": "acc_101", "to": "acc_102", "amount": 500, "currency": "MNT"}` | `201 {"result":"OK"}` |
| **2** | Negative Test (Error) | `acc_frozen` (Царцаагдсан данс), `acc_102` (Идэвхтэй) | `{"from": "acc_frozen", "to": "acc_102", "amount": 500, "currency": "MNT"}` | `200 {"result":"ERROR_FROZEN"}` |
| **3** | Different Currency | `acc_101` (USD данс), `acc_103` (USD данс) | `{"from": "acc_101", "to": "acc_103", "amount": 50, "currency": "USD"}` | `201 {"result":"OK"}` (Ханш хөрвүүлэгдсэн) |

## Дүгнэлт

Гараар боловсруулсан Category-Partition арга нь системийн бизнесийн логик, алдааны семантик болон давуу эрэмбийг нарийн хянах боломж олгодог. Харин Microsoft PICT хэрэгсэл нь олон хувьсагчийн харилцан үйлчлэлийг хосоор нь хамрах (pairwise covering array) замаар тест кейсийн тоог автоматаар эрс цөөрүүлдэг. PICT-ийн ашигладаг greedy (шунахай) алгоритм нь хосуудыг аль болох хурдан хамруулах зорилготой байдаг тул зарим үед гар аргаар олсон хамгийн цөөн мөрөөс илүү үр дүн гаргах тохиолдол байдаг. Тухайлбал, браузерын загвар дээр 2-way болон 3-way байдлаар тестийн комбинацийг өргөжүүлж туршихад мөрийн тоо хэрхэн өөрчлөгддөг нь тодорхой харагдсан юм. Шилжүүлгийн функцийн хувьд хязгаарлалтгүй (`nc`), хязгаарлалттай (`transfer`) болон сөрөг утгатай (`neg`) загваруудыг харьцуулж ажиллуулахад PICT-ийн гаралтын мөрийн тоо бодит дүрэмд суурилж өөрчлөгдсөн. Ялангуяа сөрөг утгуудыг `~` тэмдэглэгээгээр тодорхойлох нь category-partition-ий [ERROR] тэмдэглэгээтэй яг дүйцэж, нэг мөрөнд олон алдаа зэрэг орж error masking үүсэхээс сэргийлсэн. Энэхүү лабын хүрээнд хязгаарлалтын дүрэм болон сөрөг утгуудыг зөв тодорхойлох нь хамгийн их бодол шаардсан чухал алхам байв. Бодит тест кейсүүдийг гаргаж setup, input body, oracle-ийг тодорхойлсноор тестийн загварыг практикт хэрэгжүүлэх бүрэн боломжтойг ойлгосон. Эцэст нь, хоёр аргыг хослуулан хэрэглэснээр програм хангамжийн чанарын баталгааг өндөр түвшинд хангаж, хуурамч эсвэл илүүдэл тестүүдийг амжилттай хасах боломжтой юм.
